3. Why the strict decode throws (and why Solscan works)

  • A strict BorshCoder(new IDL) unconditionally reads the track_volume tag past byte 24. On a 24-byte legacy buffer that read runs past the end → RangeError: offset out of range. The data is fine; the layout assumption is wrong for that revision.
  • Solscan decodes the same bytes because it pins an older IDL revision (or falls back by length) — same remedy this page implements explicitly: pick the layout from the buffer length instead of assuming the newest IDL.
  • Second trap in the question’s snippet: the code base58-decodes by hand (bs58.decode(...)) and passes 'base58' to coder.instruction.decode. Hand this page (or the coder) exactly one form: raw bytes with no encoding flag, or the base58 string with the flag — never both. The odd <=15 / Received 16 window in the report points at a 16-byte buffer reaching the failing read, i.e. shorter than the pasted 24-byte args, which is consistent with such a double-handling (or a truncated slice) upstream of the coder.
